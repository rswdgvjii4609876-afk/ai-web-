## 二、项目概述

职启智评面向高校学生求职准备中的典型问题：岗位认知不清、简历证据不足、面试训练零散、反馈难以复盘、学习计划难以持续执行。项目不是只生成面试题或润色简历，而是把求职准备拆成一条 AI 原生训练链路：简历解析、岗位画像、证据诊断、简历润色、难度分层面试、报告复盘、学习计划、训练复盘和后台人工标注。

本项目的 AI 原生结构首先体现在产品运行链路中：AI 贯穿简历、岗位、证据、面试、报告和学习计划。用户上传简历后，系统通过 AI 和规则共同抽取结构化信息，再结合目标岗位画像形成能力诊断；后续面试、报告和学习计划都围绕同一份证据状态展开，避免每个页面各自生成孤立建议。后台治理作为独立控制面，负责授权、复核、PII 检查和样本准入，不直接作为普通用户训练步骤。

在 OPC 赛道中，项目建设过程本身也采用 AI 原生组织方式。负责人作为 `OPC Commander`，通过 Skills 能力包、Codex 工程执行、子 Agent 复审和后台治理记录，把一个人的产品、工程、测试、文档和答辩准备能力扩展成轻量化创新单元。这一建设结构是项目的支撑能力，但正式 AI 原生结构的主体仍是产品内部的 AI 运行闭环。

## 三、项目内部 AI 原生产品结构

### 3.1 产品运行主链路

职启智评的用户链路不是“输入一个问题，得到一段回答”，而是围绕求职能力提升形成连续闭环：

```text
简历解析 -> 岗位画像 -> 证据诊断 -> 简历润色 -> 难度分层面试 -> 报告复盘 -> 学习计划 -> 训练复盘
```

这条链路是用户侧能力诊断与训练闭环。后台标注、授权确认、PII 检查和样本导出不属于普通用户训练步骤，而是独立的治理门禁，用于判断哪些完成案例可以进入人工复核、评测或后续样本准备。

### 3.2 产品模块与 AI 原生作用

| 产品模块 | AI 原生作用 | 输出结果 |
|---|---|---|
| 简历解析 | 抽取教育、技能、项目、经历，并在模型坏 JSON 时修复或兜底 | 结构化简历、基础画像 |
| 岗位画像 | 整理岗位要求、面经切片和能力标准 | 目标岗位能力要求 |
| 证据诊断 | 对齐简历证据与岗位要求，区分直接证据、间接证据、声明待验证和缺失 | 能力差距、证据状态 |
| 简历润色 | 基于已有证据生成岗位化表达，不新增事实 | 润色建议、补证据建议 |
| 难度分层面试 | 按 easy / medium / hard 生成不同深度追问 | 面试题、追问目标、评分反馈 |
| 报告复盘 | 汇总回答质量、能力缺口、风险点和后续建议 | 面试报告、复盘重点 |
| 学习计划 | 根据报告和能力诊断生成可编辑、可执行、可复盘的学习计划 | 学习计划、任务、下一步行动 |
| 后台治理控制面 | 对已完成案例做授权来源、人工复核、PII 检查和导出门禁 | 可标注案例、可导出样本候选 |

### 3.3 数据与证据流转

项目内部的数据流采用“证据先行”的方式。简历中的技能、项目、经历不会直接被 AI 扩写成能力结论，而是先进入证据状态判断：

| 证据状态 | 含义 | 系统处理 |
|---|---|---|
| direct | 简历中有明确项目、职责、结果或场景支撑 | 可作为强证据进入诊断、追问和报告 |
| indirect | 有相关经历，但与目标岗位要求存在转换关系 | 可作为间接支撑，并在面试中进一步验证 |
| claimed_only | 技能栏声明具备，但缺少项目深度证据 | 给基础信用，进入面试验证和补证据建议 |
| missing | 简历中没有相关能力或证据 | 进入学习缺口或补强计划 |

每个诊断结论、润色建议和追问目标都应绑定来源：简历片段、岗位要求、面试回答或后台人工复核记录。没有来源支撑的内容只能作为待验证建议，不能写成候选人事实。该机制防止 AI 把岗位知识库内容写成候选人真实经历，也防止简历润色新增不存在的公司、项目、时间、证书、指标或技术栈。

### 3.4 面试、报告与学习计划闭环

面试不是独立功能，而是证据诊断之后的验证环节。系统会围绕候选人已经声明但缺少深度证据的能力进行追问。例如，技能栏出现 FastAPI、Redis、Docker 时，系统不会直接判断“不会”，而是把它们列为“已声明待验证”，通过项目职责、技术取舍、异常处理、部署经验等问题确认掌握程度。

报告生成后，用户可以选择本轮要提升的能力，由 AI 基于报告、岗位目标和已有任务进度生成学习计划草稿。用户可编辑计划、完成任务、记录笔记，再进入训练复盘或下一轮验证面试。这使产品从“给建议”升级为“持续训练和复盘”。

### 3.5 模型运行层与结构化输出

模型运行层位于产品业务层和治理门禁之间，负责把用户输入、岗位画像、证据状态和 prompt/schema 组织成可调用的大模型任务，并把模型输出转换为系统可读取的结构化结果。

模型运行层负责：

- 管理模型供应商、模型名称、Base URL 和用户 API 配置。
- 组织 prompt、schema、上下文摘要和输出格式要求。
- 解析结构化输出，处理坏 JSON、缺字段、字段类型错误和非法证据状态。
- 区分可恢复错误和不可恢复错误：格式异常可修复或兜底；API Key、额度、Base URL、模型名错误应快速提示用户处理。
- 写入非敏感诊断信息，例如模型来源、降级原因、结构化输出状态和重试结果。

模型运行层不直接决定候选人事实真实性、授权状态、人工复核结论或样本最终准入。事实真实性由证据来源和人工确认约束；授权和导出由后台治理门禁控制。

| 异常类型 | 处理方式 | 用户链路结果 |
|---|---|---|
| 坏 JSON、缺字段、字段类型错误 | 尝试结构化修复和归一化 | 修复成功则继续生成高质量结果 |
| 修复失败或评分超时 | 使用保守兜底模板并标记原因 | 主流程继续，结果标记为降级 |
| API Key、额度、Base URL、模型名错误 | 不吞掉错误，提示用户检查 AI 调用设置 | 当前 AI 功能暂停，用户可配置后重试 |
| 证据等级非法或来源缺失 | 降级为待验证建议 | 不进入候选人事实证据链 |

这使 AI 原生链路不是“模型成功才可用”，而是具备可恢复、可诊断、可审计的工程运行能力。

### 3.6 治理门禁控制面

治理门禁不是普通页面功能，而是产品训练闭环之后的后台控制面。它负责检查完成面试是否具备授权来源、人工复核记录、PII 检查结果和导出条件。只有满足门禁的样本，才可能进入评测、导出或后续训练准备。

治理门禁与产品运行链路的关系是：前台负责帮助用户完成诊断和训练；后台负责判断哪些结果可以被沉淀、复核和进入数据资产。二者相互连接，但责任边界不同。

## 四、OPC 人机协作建设结构

### 4.1 OPC Commander 角色

项目建设过程中，负责人不是被动使用 AI 工具，而是作为 OPC Commander 组织 AI 协作：确定目标、拆分任务、选择能力包、验收结果、决定提交和部署。AI 负责提出方案、执行修改、生成材料和发现风险；人负责事实判断、隐私边界、优先级和最终责任。

### 4.2 Skills 能力包与工程角色

项目建设使用的 Skills 不是简单角色卡，而是工程 SOP。每个 Skill 需要说明触发条件、输入契约、工作流、输出格式、质量门禁和失败兜底。这样，`AI Engineer`、`Backend Architect`、`Frontend Developer`、`Security Engineer`、`Document Specialist` 等角色能像真实工程师一样按职责审查和交付。

| 建设角色 | 主要职责 | 典型输出 |
|---|---|---|
| 策略与表达 AI | 拆解阶段目标、组织说明书和答辩口径 | 计划、问题清单、文案草稿 |
| Codex 工程执行 | 读取仓库、修改代码/文档、运行测试、生成提交 | 修改记录、验证结果、提交建议 |
| 子 Agent 复审 | 从产品、后端、前端、AI、安全、文档角度检查风险 | 必须修复项、建议优化项、测试缺口 |
| 后台与评测门禁 | 检查授权、PII、人工复核、导出和样本准入 | 治理结论、风险标记 |
| OPC Commander | 仲裁冲突、确认事实、决定提交和答辩表述 | 最终取舍、阶段结论 |

### 4.3 建设过程的科学性

建设过程本身也保留可审计证据：项目记忆、任务记录、升级流程手册、Agent Trace、测试命令、版本记录、DOCX 渲染检查和人工复核结论。每轮工程变更都尽量形成“目标 - 修改 - 验证 - 复审 - 提交”的闭环。

因此，项目的 OPC 创新不仅体现在产品内部 AI 原生训练闭环，也体现在建设过程中的可复用、可审查、可追责的人机协作方法。

## 五、产业应用场景说明

高校就业指导通常依赖线下咨询、老师经验和学生自我摸索，覆盖频次有限，反馈难以持续跟踪。普通 AI 求职工具多停留在简历润色、模拟面试或通用建议，缺少岗位画像、证据约束、学习闭环和人工治理。

职启智评面向以下场景：

- 高校就业服务中心：为学生提供低成本、高频次的岗位能力诊断和训练。
- 学院就业辅导：围绕不同专业和岗位方向建立能力画像与训练计划。
- 创新实践课程：把学生项目、简历表达、面试训练和复盘形成可记录成果。
- 个人求职训练：让学生从“改一份简历”升级为“持续补能力、补证据、做验证”。

项目的产业价值在于把就业辅导从一次性咨询变成可拆解、可执行、可复盘的 AI 原生训练流程。

## 七、主体治理、合规边界与补实路线

本项目按个人主体申报，负责人承担项目方向、系统运行、材料真实性和最终答辩责任。AI 只作为协作工具和运行时能力，不替代人的事实判断与合规责任。

| 事项 | AI / 系统处理 | 人类确认 |
|---|---|---|
| 简历与面试 | 抽取、诊断、追问、评分和报告草稿 | 确认真实性和是否采纳 |
| 学习计划 | 生成草稿、任务、材料和下一步建议 | 编辑计划、执行任务、记录复盘 |
| 样本治理 | 标记授权来源、PII 检查、格式校验 | 人工复核、授权材料确认、导出决策 |
| 工程提交 | 生成代码、文档、测试结果 | 决定是否提交、部署和写入材料 |
| 答辩材料 | 组织说明书、讲稿和问答草稿 | 承担最终表述责任 |

合规边界如下：

- 原始简历、真实问答、邮箱、手机号、身份证号、API Key 不进入公开材料。
- 使用“去标识化 / 脱敏”表述，不宣称完全匿名化。
- 后台记录授权确认来源与人工复核信息，不能替代用户真实授权。
- 演示样本、Preview 评测和 AI 模拟回答不写成真实用户完整面试数据。
- 岗位知识库内容不能写成候选人真实经历。

### 7.1 三个月补实路线

| 时间 | 目标 | 验收物 |
|---|---|---|
| 第 1 个月 | 完成真实授权案例闭环 | 授权记录、完成面试、报告、学习计划、后台人工标注 |
| 第 2 个月 | 建立评测与样本治理集 | 脱敏样本、人工评分一致性记录、PII 检查、导出门禁 |
| 第 3 个月 | 做真实后训练或对照评估准备 | 官方任务记录或对照评估报告、高校试点反馈 |

在官方训练任务、模型记录和真实对照评估完成前，材料只能说明“已具备准备链路和门禁设计”，不能写成已经完成正式训练成果。
