# 评委问答库

## 一、是否只是套壳大模型 API？

**问：这个项目是不是只是把 DeepSeek 或 OpenAI 接到一个面试页面里？**

答：不是。普通套壳工具的核心是聊天，本项目的核心是证据约束型就业训练闭环。系统包含简历解析、岗位画像、RAG 数据库、证据诊断、难度分层面试、报告复盘、学习计划和后台治理门禁。大模型只是其中的推理和生成层，外面还有结构化数据、证据规则、异常修复、人工复核和样本准入。

## 二、RAG 数据库有什么作用？

**问：RAG 数据库具体做什么？**

答：RAG 数据库沉淀岗位要求、面经、能力项和学习资料。它不是用来编造候选人经历，而是作为岗位要求和追问依据。比如目标岗位是 Python 后端，系统会检索该岗位需要的 API 设计、数据库、并发、部署等能力，再对照简历证据生成诊断、追问和学习建议。

## 三、如何避免 AI 编造简历经历？

**问：AI 会不会把岗位知识库里的内容写成学生自己的经历？**

答：系统把信息来源分开：岗位知识库只能作为岗位要求和追问参考，候选人经历只能来自简历、回答和用户确认材料。诊断时使用“有明确证据、有相关经历、只声明待验证、暂无证据”四类状态，避免把“岗位要求”误写成“候选人事实”。

## 四、评测和模型优化数据治理怎么讲？

**问：你提到评测和模型优化数据治理，具体是什么？**

答：项目把微调和评测设计成后台治理体系的一部分。流程是：完成面试和报告后，后台沉淀授权案例、人工复核记录、评分记录和 PII 检查结果；通过样本门禁后，形成可用于对照评测和岗位化优化的数据基础。这个闭环服务于后续垂直模型优化，让模型更懂高校就业辅导场景。

## 五、和普通 AI 面试工具区别在哪里？

**问：市面上也有 AI 面试工具，你的差异是什么？**

答：普通 AI 面试工具通常止步于“提问和打分”。职启智评从简历证据开始，对照岗位画像诊断能力，再进入难度分层面试，面试后生成报告和学习计划，后台还能进行人工复核和样本治理。它不是单次面试，而是持续训练系统。

## 六、项目完成度如何？

**问：现在能跑到什么程度？**

答：项目已形成可演示的端到端原型和核心业务闭环。用户端主流程可以展示简历解析、能力诊断、润色、面试、报告和学习计划草稿；后台治理与评测/微调链路以可审计的数据结构、门禁流程和落地路线呈现，不把治理链路包装成大规模线上验证结论。

## 七、技术难点是什么？

**问：最大的技术难点是什么？**

答：最大难点不是调用模型，而是让模型输出稳定进入业务系统。具体包括：简历解析和证据抽取、RAG 检索边界、结构化 JSON 输出、坏 JSON 修复、长回答评分超时兜底、多轮面试记忆、后台样本门禁，以及不把知识库内容混入候选人经历。JSON 修复只处理格式层，修复后还要经过 schema 校验、字段范围检查和业务兜底。

## 八、隐私和授权怎么处理？

**问：学生简历和面试数据涉及隐私，怎么处理？**

答：系统设计了后台治理控制面。样本进入评测或后续模型优化前，需要授权来源、人工复核、PII 检查和导出门禁。管理员补授权不能表述为用户主动授权，必须记录管理员、时间、原因和确认来源。

## 九、应用场景在哪里？

**问：这个项目适合在哪里落地？**

答：主要场景有三个：高校就业中心用于批量辅导学生，学院实践课程用于训练岗位能力，个人用户用于求职准备。系统也可以为学院提供岗位能力差距统计，帮助就业辅导从经验判断变成数据化支持。

## 十、为什么这个项目有社会价值？

**问：社会价值是什么？**

答：大学生求职训练往往依赖个人经验和临时辅导，资源不均衡。职启智评把岗位要求、个人证据、面试反馈和学习计划标准化，让更多学生获得可持续的求职训练支持，也让老师能更清楚地看到学生能力差距。

## 十一、如果评委追问真实性

**问：你讲的创新很多，怎么证明不是概念？**

答：现场可以演示从简历上传到诊断、面试、报告和学习计划的完整链路。项目不是只停留在方案文档，而是包含前端、后端、后台和工程测试。对于评测集、RAG 扩展和模型优化候选路线，项目采用的是产品能力架构和一年内落地路径表达，不编造具体线上评测数字或模型编号。

## 十二、如果评委问最大短板

**问：当前最大的短板是什么？**

答：最大短板是需要继续扩大真实场景样本和高校试用反馈。项目当前已经具备可演示核心闭环和治理门禁设计，下一步重点是沉淀更多授权案例，建设岗位评测集，持续优化 RAG 知识库和岗位化追问策略。
