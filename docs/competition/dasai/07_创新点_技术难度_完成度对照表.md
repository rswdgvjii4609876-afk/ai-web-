# 创新点、技术难度、完成度对照表

| 评分项 | 职启智评对应内容 | 答辩表达重点 |

| 项目技术难度 | 简历解析、岗位画像、RAG 检索、结构化输出、坏 JSON 修复、多轮面试、后台门禁 | 不是简单聊天，而是工程化 AI 流程 |
| 项目创新度 | 证据约束型就业训练闭环、难度分层面试、报告到学习计划、评测与模型优化数据治理链路 | 从一次性建议升级为持续训练系统 |

| 队员贡献程度 | 一人主导产品定义、工程实现、测试验证、文档答辩，并使用 AI 工具进行代码审查、文档复核和任务管理 | 突出超级个体工程组织能力 |
| 答辩表现 | 普通人能听懂的流程、清晰回答边界 | 少堆术语，多讲用户路径 |

## 核心创新与技术难度

| 创新点 | 技术难度 | 完成度表达 |
|---|---|---|
| 岗位画像与 RAG 数据库 | 需要把岗位要求、面经、能力项和学习资料切片、检索、路由到面试和报告 | 作为产品能力架构和知识底座讲解 |
| 简历证据诊断 | 需要区分明确证据、相关经历、声明待验证和暂无证据，避免误判 | 已形成诊断口径和面试追问策略 |
| 难度分层 AI 面试 | 需要不同难度对应不同题型策略，并结合岗位和简历证据 | 已形成 easy/medium/hard 的产品策略 |
| 报告到学习计划闭环 | 需要把评分结果转为可执行任务，而不是只给一句建议 | 已形成从报告勾选能力到学习计划的闭环设计 |
| 评测与模型优化数据治理链路 | 需要授权、人工复核、PII 检查、样本门禁和对照评测 | 作为系统治理和模型优化基础讲解 |

| 多 Agent 建设方式 | 一人项目需要产品、工程、测试、文档多角色协作 | 使用 Skills、Codex 和子 Agent 形成审查闭环 |

## 完成度讲法

可以说：

- 项目已具备可演示的端到端原型和核心业务闭环。
- 用户端、后端、后台和文档材料已经形成一套闭环。
- RAG、评测、样本治理和微调路线作为核心创新体系的一部分，服务于系统持续优化。

现场表达保护线：

- 给出未经验收的模型编号。
- 给出未经验收的大规模线上评测数字。
- 把样本治理路线说成全部真实样本已完成验收。

## 技术可信度讲法

这个项目的技术可信度来自四个方面：

1. AI 输出可结构化：简历、评分、报告、学习计划都进入系统字段。
2. AI 输出可约束：岗位知识不等于候选人经历。
3. AI 异常可兜底：坏 JSON、超时、长回答不会让流程永久卡住；格式修复后仍要经过 schema 校验和业务字段兜底。
4. 数据流转可治理：授权、复核、PII 和样本门禁决定数据能否进入评测与模型优化。
